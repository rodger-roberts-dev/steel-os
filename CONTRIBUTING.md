# Contributing to Steel OS

Welcome to the Steel & Code virtual blacksmith shop. We value curiosity, practical engineering, thoughtful design, and respectful collaboration.

## The forge rule

> **Measure twice, code once. And ask the architect before building another company.**

This is a friendly reminder that shipping quickly does not replace agreeing on what we are building.

Before starting a major feature or creating a new product, service, or repository:

1. **Check the plan.** Read the relevant Jira story, acceptance criteria, and architectural decisions.
2. **Confirm product boundaries.** Determine whether functionality belongs in Steel OS, an independent project (such as Steel Shield), or an integration layer.
3. **Ask before expanding scope.** Obtain a product/architecture decision before introducing a new standalone product, repository, service, dependency, or major user-facing behavior not already approved.
4. **Build incrementally.** Prefer small, reviewable pull requests with clear tests and rollback paths.
5. **Verify before declaring done.** A merged PR is not the same as passing acceptance tests, installer checks, hardware tests, or user review.
6. **Keep the architect in the loop.** Surface tradeoffs and deviations explicitly; do not silently change an agreed design.

AI collaborators and human contributors follow the same rules. Initiative is encouraged; unreviewed architectural changes are not.

## Working agreement

- **Design decides what and why.** Engineers choose how within the approved boundaries.
- **Jira captures requirements and decisions.** GitHub captures implementation, review, tests, and releases.
- **A change of plan is welcome when discussed.** Update the issue and obtain approval *before* treating the new direction as settled.

Let's build excellent tools, one deliberate swing of the hammer at a time. 🔨
